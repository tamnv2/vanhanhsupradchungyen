# CHANGE RECORD — LAN PILOT 0.8.0

Change ID: `LAN-20260911-04`
Time: 2026-09-11
Environment: BETA LAN pilot only
Stable impact: NONE
Cloud BETA Worker/D1 impact: NONE

## Reason

Owner requested correction of Agent/APK update behavior, fixes for realtime issues detected from prior physical diagnostics, substantially richer diagnostics, and resource/battery policy optimized for the restricted corporate laptop and Newland MT90 devices.

The requested lifecycle is now explicit: foreground app uses LAN realtime; when the UI leaves foreground, realtime stops; only unfinished work/durable queue recovery may continue in a bounded foreground service; after finishing, background work stops and the next app open resumes discovery/sync/realtime.

## V4 Windows Agent changes

- startup switched to `V4Program`;
- one release version is injected into the Agent, APK and GitHub Release;
- updater compares semantic versions instead of treating any prerelease tag as an update;
- manual update downloads exact Agent ZIP + SHA256, verifies digest, stages in per-user writable storage and restarts without Administrator;
- staged update has post-restart `/health` probe and rollback path;
- fixed a batch-script defect where `%HEALTH_OK%` inside a parenthesized block was expanded before the loop and made the success branch unreachable;
- CI now rejects that stale pattern and requires reachable health-success, SHA256 verification and rollback source invariants;
- realtime stream uses per-Agent `streamEpoch` plus sequence numbers;
- Agent restart/old cursor and bounded-buffer gaps are explicitly surfaced for client resync;
- realtime long-poll wakeup is signal-driven instead of 50 ms active polling;
- physical PDA and synthetic load client metrics are separated;
- cancelled long-poll requests are separated from genuine service errors;
- diagnostic/runtime/network/update/realtime/transfer counters were expanded;
- Agent remains portable user-mode/asInvoker with tray/settings/dashboard and no router/DNS/firewall/Admin dependency.

## V4 Android changes

- launcher switched to `MainActivityV4`;
- update flow uses semantic version comparison, exact APK + SHA256 assets, SHA256 verification, package/version verification, FileProvider and Android's normal package installer;
- manual GitHub Release fallback remains available if automatic/manual in-app install cannot proceed;
- realtime handles Agent epoch change by resetting cursor and recalibrating instead of remaining stuck on a pre-restart sequence;
- buffer overrun explicitly triggers resync accounting;
- cross-device display latency now uses a five-sample Agent clock calibration and best-RTT offset estimate;
- publish/ACK latency uses monotonic clock on the same PDA;
- foreground-only realtime policy implemented;
- `LanFinishService` is `START_NOT_STICKY`, uses a bounded partial wakelock only while necessary, waits for already-running work, attempts bounded durable-queue recovery, then stops itself;
- if the Activity is destroyed while a tracked task is still running, the task may finish; once the final tracked task completes, the Activity executor/database are explicitly released;
- durable queue survives unsuccessful recovery and resumes on a later app open;
- additional lifecycle, battery/power, queue, discovery, realtime, clock, transfer and update diagnostics are exported.

## Build failures found and corrected during hardening

The regression process intentionally blocked publication until compile/source/version gates were satisfied. Defects found included:

- AndroidX dependency without `android.useAndroidX=true`;
- malformed C# interpolated/raw updater string;
- Android `Debug.getPss()` integer type mismatch;
- Android `BuildConfig` generation not enabled for updater/version code;
- staged Agent updater health-success logic defect;
- Activity post-background-job resource cleanup gap;
- two transient CI invariant checks whose patterns did not match the correct source and were corrected.

These were fixed before the final candidate.

## What is PASS now vs still physical

Automated source/build/sign/version/package/release gates are PASS.

The LAN feasibility/release gate is NOT yet declared fully PASS because these requirements can only be proven on the real restricted laptop + two MT90:

- actual no-admin staged Agent replacement and health/rollback behavior;
- automatic update notification/manual fallback on deployed old versions;
- Android installer flow under the MT90/company policy;
- restart/reacquisition and epoch resync on the real LAN;
- realtime latency/gap behavior under normal/heavy concurrent physical use;
- transfer throughput/stability;
- Wi-Fi-off durable queue recovery with zero unexplained loss;
- foreground/background finish-service behavior and battery/resource footprint;
- synthetic 10/25/50/100 Agent capacity plus soak;
- final diagnostic export analysis.

RF/Wi-Fi behavior above two physical MT90 remains explicitly unproven.
